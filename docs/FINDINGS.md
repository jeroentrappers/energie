# Findings

Live-behaviour oddities found while porting. Most were fixed in Home Assistant on 2026-11-07
(`the original configurationfixes_2026_11_07.py` is the exact patch; the config from before
it is kept in `the earlier configuration`), and the port follows the fixed config. What is still
open is reproduced faithfully and marked `// LIVE:` in the code.

## Fixed in HA on 2026-11-07

The port reproduces the new behaviour. The old one is described for reference, and for reading
the replay of recorder history from before the fix (`REPLAY.md`).

## Still open, or not a config issue

| Where | What | Effect / why not changed |
| --- | --- | --- |
| `sensor.batterij_setpoint` | The `not ev_batterij_auto_laden` clause of the `ev_grid_parked` branch can never be false (parked needs no car drawing, the dump flag needs one). | Dead code, no effect. Still in the template; `// LIVE:` in `battery.rs`. |
| `neg_injectie_herstel` | Resets the backflow limit to 5500 W but leaves the feed-in limit switch that `neg_injectie_curtail` turned on. | Not changed in HA: the feed-in limit switch is normally on, so leaving it on is the baseline. |
| `P1 mediaan 90s` (statistics) | The entity id says 90 s, `max_age` is 10 s. | Not changed in HA: the entity registry name is already "P1 mediaan (10s)"; only the id is historic. |
| `ev_laden_buzz` / `ev_laden_cable` `grid_max` | LOGIC.md describes the peak yield as `resv_eff = max(0, resv − battery_charge)` with `load` including the battery. Live: `load` excludes the battery's charge and the car yields `max(batterij_reservering_effectief, resv_target)` in full. | Documentation drift only; the live formula is self-consistent. |
| `solis_modbus` (drivers) | The config entry polls the 43xxx settings group "slow": `poll_interval_slow: 300` s. HA's view of the RC mode/powers/timeout, the grid-charge and feed-in switches and the backflow limit can be 5 min old, except right after HA itself writes them. The options also disagree with the data (`connection: S2_WL_ST` vs `WAVESHARE`, `has_ac_coupling` false vs true). | Integration-internal, not changed. The port polls every block each read; it sees changes (RC timeout reverting to mode 0, writes from the Solis app) up to 5 min sooner than HA. |
| `solis_modbus` RC select (drivers) | Selecting an RC mode writes 43135 and then re-writes 43136, 43129 and 43282 *from the register cache* (`companion_writes`). With the 5 min cache, a setpoint changed outside HA is overwritten with the stale cached value. | Integration-internal. Reproduced (the port's cache is fresher, so the window is smaller). |
| `solis_modbus` RC select companions (control) | Every dispatcher run (30 s) selects the RC mode, and the select always writes 43135 and re-writes 43136, 43129, 43282: about 13 000 register writes a day (the simulated day: 12 999). A companion with no cached value is skipped, so right after a reload a forced mode can be enabled without its timeout being re-written. | Integration-internal. Reproduced write for write; energie writes the fallback timeout (10 min) when 43282 is not cached or not 1..30 (`docs/CONTROL.md`). Whether these registers wear the inverter's flash is not documented. energie does not select a mode the inverter already holds: a held forced mode only gets a 43135 keepalive every 5 minutes, `None` nothing (the simulated day: 2 144 writes instead of 12 999, `docs/CONTROL.md`). |
| `solis_modbus` SoC (drivers) | `spike_filtering` holds a 0 or 100 % SoC reading back until it is seen on 3 consecutive polls. | Integration-internal. A battery that reaches 100 % shows 99 % for two more polls; reproduced. |
| `entsoe` vs `price_backup.py` (drivers) | `sensor.jeroen_current_percentage_in_electricity_price_range` (8.5 % at 13:47 on 2026-11-07) and `sensor.stroomprijs_positie` (18.6 %) disagreed: both use "today from 00:00 plus tomorrow when known", but the `entsoe` integration had not loaded tomorrow yet while energy-charts already served it. On a flat day `entsoe` answers 100 %, `price_backup.py` 0 %. | Integration-internal. The port implements the `entsoe` formula over whatever is published (100 % on a flat day); right after publication it reads 18.6 %, not HA's 8.5 %. |
| `price_backup.py` docstring (drivers) | Says ENTSO-E has answered 503 since 2026-08-30. On 2026-11-07 the A44 query answered 200 with both days (191 points: one quarter left out by A03 compression). | ENTSO-E works again as fallback; the port fills the compressed position like the integration. |
| `number.smartevse_1234_charge_current_override` (drivers) | The discovery `command_template` is `{{ value \| int * 10 }}` with step 1, so setting the number from HA truncates to whole amps; the automations bypass it and publish tenths on `Set/CurrentOverride` directly (seen live: `151`). Its `max` (29) is static discovery data. | SmartEVSE discovery data, not changed. The port publishes tenths like the automations. |
| `omnik_inverter` (drivers) | The config entry's `scan_interval: 4` is minutes: `sensor.omnik_hoofddak_..._current_power_production` changes at most every 4 min. | Integration-internal, not changed. Surplus maths on the Omnik power in HA works on a value up to 4 min old. |
| HomeWizard P1 (drivers) | The meter's TLS certificate names `<serial>.p1dongle.device.homewizard.energy` (SAN) under the X.509 v1 "Appliance Access CA"; HA's `homewizard_energy` client checks the name only when it is given the device identifier (otherwise chain only) and sends no `X-Api-Version` header, which the v2 API accepts. | Integration-internal, not changed. The port verifies chain and SAN name and sends the header; checked against the live meter with one read-only GET. |
| `core::jinja::round` (port) | Multiply-round-divide was not Python's `round(x, n)` when the scaling lands on a tie the exact binary value does not have, e.g. `round(1.649535, 5)`. | Port-only, already fixed: `jinja::round` rounds the exact binary value (0 mismatches on 20 000 random CPython cases). |
